# 槽位 rig 演化

当前落地为可选的刚性槽位运行时，默认仍使用现有精灵帧。BaseRig 固定规范坐标和绘制顺序；SlotRegistry 原子替换已解码且经外部 QA 的图像；RigPlayer 按槽位中心旋转绘制，控制器驱动时间，PetView 可切换渲染。图像由调用方持有并负责释放，替换不能提前释放仍被其他槽位引用的图像。

优势：动作与纹理解耦，同一动作复用不同配件；有限轨道与角度约束降低生成结果风险；未知槽位拒绝发布，避免隐式改变身份结构。保留旧路径便于逐步迁移。

代价：透明 PNG 不自带锚点、遮挡和骨骼权重。统一坐标并不能保证围巾不遮下巴，qa_anchor 只是验收要求，需要人工或视觉模型实际检查。当前只实现刚性单层槽位，没有父子骨骼、网格、弹簧或蒙皮，不能等同于 Spine/Live2D。接入这些引擎时应保留指令协议，另写渲染适配器。

发布流程：LLM 槽位指令 → 校验已知槽位及动作 → 以 canonical_base 生成候选 → 检查透明度、尺寸、身份与 qa_anchor → 解码 → apply → 重绘。失败保持旧组件；并发生成需在服务层加入 revision 比较，过期结果不得覆盖新结果。当前尚未实现生成服务、持久化、版本回滚和 QA 执行器，qaPassed 必须来自可信服务而非 LLM 自报。

动作流程：上游将结构化 motion_spec 转为 ParametricRigMotion，校验时长、数量、有限值、严格递增时间和角度。MotionRegistry 校验槽位，未知事件回退静止模板。生产发布还需加入 idle/tap/drag 经人工验收的基准动作、事件优先级和中断策略。当前控制器循环播放已选择动作，未接入事件选择。

迁移顺序：先准备一套人工验收的透明拆件与规范坐标；创建 SlotRegistry，填充组件后将 RigPlayer 注入 controller.rigPlayer；验证镜像、缩放、拖动和命中范围；再接入动作 JSON、事件触发、生成任务及版本化存储。新骨架必须新建 rig 版本并显式迁移，不能通过 replace 指令实现。

用户所列 See-Through、img2rig、Reskin Studio 等作为候选工具，本文不将其能力视为已验证事实；选型前需独立核对许可证、透明组件输出质量和目标平台支持。
